# ShopOS Deployment and Local Setup

ShopOS deploys as **one service plus a database**: a single container runs the API and
serves the web app from the same address, and MongoDB Atlas provides the database.
The recommended host is Render, because `render.yaml` describes the whole service,
but any host that runs a Dockerfile works the same way.

```
 browser ── https ──> [ one container: API + built web app ]  (Render, Railway, Fly, a VPS)
                                   │
                                   └── mongodb+srv ──> MongoDB Atlas (a replica set)
```

One address for pages and API means the sign-in cookie stays first-party and there
is no CORS to configure.

---

## Deploy to production: Render + MongoDB Atlas

About 20 minutes the first time. You need a GitHub account with this repository, a
MongoDB Atlas account and a Render account (both have free tiers).

### 1. Create the database (MongoDB Atlas)

1. Sign in at <https://cloud.mongodb.com> and **create a cluster**. The free **M0**
   tier is enough to start. Choose **AWS, Singapore (ap-southeast-1)** so it sits
   next to the Render region below. Every Atlas cluster is a replica set, which
   ShopOS needs for transactions.
2. **Database Access** -> add a database user with a password, role *Read and write
   to any database*. Use letters and digits only in the password, so it needs no
   escaping inside the connection string.
3. **Network Access** -> add `0.0.0.0/0` (allow from anywhere). Render's free and
   starter plans do not have fixed outgoing addresses. The strong database password
   is what protects the cluster; on a paid plan with static IPs you can narrow this.
4. **Connect -> Drivers** and copy the `mongodb+srv://...` string. Put the database
   name before the `?`:

   ```
   mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/shopos?retryWrites=true&w=majority
   ```

   That string is a password; do not paste it into chat, tickets or the repository.

### 2. Create the service (Render)

1. Sign in at <https://render.com> with GitHub.
2. **New -> Blueprint**, pick the `ShopOS` repository. Render reads `render.yaml` and
   shows one web service called `shopos`.
3. Fill in the values it asks for:
   - `MONGODB_URI` - the string from step 1.4.
   - `GOOGLE_CLIENT_ID` - optional; leave empty to hide Google sign-in for now.
   - `CLOUDINARY_*` - optional; leave empty to disable product images.

   `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render.
4. **Apply**. The first build takes about five minutes. When it is live, the service
   page shows its address, such as `https://shopos-abcd.onrender.com`.

On boot the server connects, builds any missing database indexes (the unique ones
that stop duplicate emails or invoice numbers), runs pending data migrations, then
starts taking requests. Render only switches traffic over once
`/api/v1/health/ready` answers, so a broken deploy never replaces a working one.

### 3. Check it from outside

```bash
npm run check:deploy -- https://shopos-abcd.onrender.com
```

Read-only. It checks readiness, that the database supports transactions, production
mode, the app and a deep link, JSON 404s under `/api`, 401 without a session, that
other websites and operator injection are refused, the security headers, the HTTP to
HTTPS redirect and caching. Every line should be PASS. On the free plan the first
request may take a minute while the service wakes.

### 4. Create the first account

Open the address and choose **Create your account**. That person is the owner of the
first business. Do not run `npm run seed` against production: the demo business is
for development and demos.

### 5. Turn on Google sign-in (optional)

1. In Google Cloud Console -> APIs & Services -> Credentials, open the OAuth client
   whose id you will use.
2. Under **Authorised JavaScript origins** add the Render address exactly
   (`https://shopos-abcd.onrender.com`, no trailing slash) and save.
3. In Render -> the service -> Environment, set `GOOGLE_CLIENT_ID` and save. Render
   restarts the service; the button appears on the sign-in page. No rebuild is needed:
   the page asks the API whether Google is configured.

### 6. Your own domain (optional)

Render -> the service -> Settings -> Custom Domains. Render issues the certificate.
Add the new address to the Google origins as well.

### Free plan versus a paid one

The free web service sleeps after 15 idle minutes and takes about a minute to wake,
and the hourly overdue sweep does not run while it sleeps. That is fine for a demo or
a review. For a shop that people work in every day, set `plan: starter` in
`render.yaml` (or change it in the dashboard), and consider an Atlas tier with
continuous backups.

### Updating

Push to `main`. Render rebuilds and redeploys automatically (`autoDeploy: true`), and
CI runs the same tests against a real replica set and boots the production image
before you would merge anything risky.

### Backups

The free M0 tier has no automatic backups. Before relying on the data, either move to
a tier with backups, or export it on a schedule with the MongoDB Database Tools:

```bash
mongodump --uri "mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/shopos" --out backup-2026-11-04
```

A backup is only proven by restoring it, into a separate database:

```bash
mongorestore --uri "mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net" --nsFrom "shopos.*" --nsTo "shopos_restorecheck.*" backup-2026-11-04
```

### Moving local data to production (optional)

The same tools copy a local database to Atlas, for example the demo shop built on
this machine:

```bash
mongodump --uri "mongodb://127.0.0.1:27018/shopos?replicaSet=rs0" --out local-export
mongorestore --uri "mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net" --nsInclude "shopos.*" local-export
```

That copies everything in the local database, including every account and the older
seeded demo business. Restore into an empty Atlas database only.

## Deploy anywhere else (any Docker host)

The root `Dockerfile` is the production image. It needs the variables in
[`deploy/production.env.example`](../deploy/production.env.example): a
`MONGODB_URI` pointing at a replica set and two different JWT secrets of 32+
characters. It follows the `PORT` the host sets (default 4000), runs as a non-root
user and has a health check.

```bash
docker build -t shopos .
docker run -p 4000:4000 --env-file production.env shopos
```

Put HTTPS in front of it: the sign-in cookie is `Secure` in production, and browsers
send it over plain HTTP only to `localhost`. `*.env` files are git-ignored so a
filled-in copy cannot be committed.

CI builds this image on every push, starts it against a real MongoDB replica set and
checks that it serves the app, keeps `/api` 404s as JSON, refuses data without a
session and can register a business end to end.

## Local setup

### Requirements

- Node.js 20 or newer (developed on 24)
- npm 10 or newer (workspaces)
- MongoDB 6 or newer, as a replica set (see below)

```bash
npm install
cp apps/api/.env.example apps/api/.env
```

Edit `apps/api/.env` and set `MONGODB_URI` - the only required value. Every other
key is optional and documented in [keys-and-secrets.md](keys-and-secrets.md).

Load the demo business (safe to re-run at any time):

```bash
npm run seed
```

Then start both sides:

```bash
npm run dev
```

- API: http://localhost:4000/api/v1
- Web: http://localhost:5173

The Vite dev server proxies `/api` to the API, so the browser only ever talks to
one origin during development too.

Verify the whole stack from **Administration -> System Status** in the web app,
or directly:

```bash
curl http://localhost:4000/api/v1/health
```

### Trying the production build locally

```bash
npm run build
```

Then run the bundle with `NODE_ENV=production`, two real secrets and
`WEB_DIST_DIR` pointing at `apps/web/dist`, and open <http://localhost:4000>:
one process serves the site and the API, exactly as in production.
`npm run check:deploy -- http://localhost:4000` should pass every check.

## MongoDB must be a replica set

Multi-document transactions require a replica set or a sharded cluster. A
standalone `mongod` cannot run them, and ShopOS needs them for stock transfers,
goods receipts, invoices, returns and payments.

The API detects this at startup. Standalone logs a warning, and System Status
shows **Multi-document transactions: Unavailable**.

### Option A - MongoDB Atlas

Any Atlas cluster, including the free tier, is already a replica set. Use its
connection string as `MONGODB_URI`.

### Option B - one command (recommended for development)

```bash
npm run db:local
```

starts a private single-node replica set on port 27018 with its own data
directory (`data/mongo-dev`), leaving any system MongoDB untouched. Then use:

```
MONGODB_URI=mongodb://127.0.0.1:27018/shopos?replicaSet=rs0
```

### Option C - edit your own mongod

A single node is still a replica set, so this is enough for development.

Add to your `mongod.cfg` (Windows: `C:\Program Files\MongoDB\Server\<v>\bin\mongod.cfg`):

```yaml
replication:
  replSetName: rs0
```

Restart the MongoDB service, then initialise it once:

```bash
mongosh --eval "rs.initiate()"
```

Point the API at it:

```
MONGODB_URI=mongodb://127.0.0.1:27017/shopos?replicaSet=rs0
```

System Status should then read **Topology: replicaSet**, **transactions:
Supported**.

## Environment variables

Development: `apps/api/.env.example`. Production: `deploy/production.env.example`.
Never commit a filled-in copy of either.

| Variable | Required | Notes |
|---|---|---|
| `NODE_ENV` | yes | `development`, `test` or `production` |
| `PORT` | no | Default 4000. Most hosts set it |
| `MONGODB_URI` | yes | Must be a replica set (Atlas is one) |
| `JWT_ACCESS_SECRET` | yes in production | 32+ random characters. `openssl rand -hex 64` |
| `JWT_REFRESH_SECRET` | yes in production | Must differ from the access secret |
| `WEB_DIST_DIR` | no | Folder of the built web app. When set, the API serves the site too. The Docker image sets it |
| `CORS_ORIGINS` | no | Only for *other* websites that must call the API. The app's own address is always allowed |
| `SYNC_INDEXES` | no | Default true. Builds missing indexes at startup; production relies on it |
| `ACCESS_TOKEN_TTL` | no | Default `15m` |
| `REFRESH_TOKEN_TTL_DAYS` | no | Default 30 |
| `COOKIE_DOMAIN` | no | Only when the site and API are on different subdomains |
| `GOOGLE_CLIENT_ID` | no | Google Sign-In. Hidden when absent |
| `GOOGLE_CLIENT_SECRET` | no | Reserved for future OAuth flows |
| `CLOUDINARY_*` | no | Product images. Upload disabled when absent |
| `LOG_LEVEL` | no | Default `debug`; use `info` in production |
| `JOBS_ENABLED` | no | Default true. Hourly overdue sweep; false on all but one instance |
| `TEST_MONGODB_URI` | tests only | Its name must contain `test`. Default `mongodb://127.0.0.1:27018/shopos_test?replicaSet=rs0` |
| `GENERAL_RATE_LIMIT`, `AUTH_RATE_LIMIT` | no | Override the per-IP limits |

Production boot fails if a JWT secret is still a placeholder, shorter than 32
characters, or the same as the other one. That is deliberate.

## Health checks

| Endpoint | Use |
|---|---|
| `/api/v1/health/live` | Liveness. Restart the container when this fails |
| `/api/v1/health/ready` | Readiness. 503 while the database is unreachable, so traffic is withheld |
| `/api/v1/health` | Full status, for humans |

## Docker Compose (everything on one machine)

```bash
cp deploy/.env.example .env      # set JWT_ACCESS_SECRET and JWT_REFRESH_SECRET
docker compose up -d --build
docker compose --profile tools run --rm seed     # optional: the demo business
```

This runs MongoDB as a replica set, the API, and nginx serving the web app on
<http://localhost:8080> (change with `WEB_PORT`) - a self-hosted alternative to the
single-container image above.

| Service | Image | Notes |
|---|---|---|
| `mongo` | `mongo:7` | Started as a one-node replica set; a healthcheck initiates it on first run. Data in the `mongo-data` volume |
| `api` | `deploy/api.Dockerfile` | Production dependencies and the tsup bundle only, non-root, healthcheck on `/health/ready` |
| `web` | `deploy/web.Dockerfile` | The Vite build behind nginx, which forwards `/api` to the API and falls back to `index.html` for client routes |
| `seed` | api image, `tools` target | One-off demo data; only with `--profile tools` |

Notes:

- Compose refuses to start without both JWT secrets, and the API refuses to boot in
  production with placeholders.
- CI builds both images on every push, but `docker compose up` itself has not been
  run in CI; treat the first run as its test.
- To run more than one API container, move rate limiting to a shared store and set
  `JOBS_ENABLED=false` on all but one (see [security.md](security.md)).

## Tests and CI

```bash
npm run db:local        # once, in its own terminal
npm test
```

The API specs need a replica set because the code under test uses transactions.
They connect to `TEST_MONGODB_URI` and **drop that database** at the start of a run;
the harness refuses to touch a database whose name does not contain `test`.

`.github/workflows/ci.yml` runs on every push and pull request:

1. **Typecheck, test, build** - starts MongoDB 7 as a replica set
   (`.github/scripts/start-mongo.sh`), installs with `npm ci`, typechecks, runs all
   tests, builds both apps and runs `npm audit` on production dependencies (fails on
   high severity).
2. **Production image** - builds the root `Dockerfile`, runs it against the replica
   set and checks it end to end, then builds the two docker-compose images.

The lockfile must list every platform's native binaries (esbuild, Tailwind,
Rolldown) or `npm ci` fails on Linux. If you regenerate it, do so from a clean
install (`rm -rf node_modules package-lock.json && npm install`), not on top of an
existing `node_modules`.

## Verifying a development server

```bash
npm run smoke
```

It reseeds the demo business, then signs in, searches the catalogue, checks every
pricing slab boundary, refuses invalid rate cards, moves stock, buys on a purchase
order with partial receipts, invoices, cancels, takes and refuses payments, and
confirms that branch-scoped staff cannot reach another branch. All 56 checks must
pass. **Never run it against production**: it rewrites the demo business. Use
`npm run check:deploy` there instead.
